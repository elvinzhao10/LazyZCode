# LazyZCode v1.3.0: supported route

v1.3.0 was the previous published stable release. This historical guide
documents its route and does not establish current host activation; v1.3.1 is
the current stable release.

v1.3.0 adds dual activation: an explicit start-work command and a plain
natural-language implementation request converge on the same execution
authority and gates. Explanation, quoted-command, or explicit plan-only
requests never mutate product files.

Prerequisites for the published v1.3.0 package: **Node.js LTS 20 or newer** and **Git** must be available on
PATH for the lifecycle entrypoint and launcher commands below.

1. Clone the published v1.3.0 release tag and use its durable
   lifecycle entrypoint:

   ```bash
   git clone --branch v1.3.0 https://github.com/elvinzhao10/LazyZCode.git
   node "<checkout>/plugins/lazyzcode/scripts/lazyzcode-lifecycle.js" onboard \
     --source https://github.com/elvinzhao10/LazyZCode/releases/tag/v1.3.0 \
     --install-root "<absolute-install-root>" --project "<absolute-project-root>" --json
   ```

2. Use the installed launcher for package checks:

   ```bash
   node "<install-root>/LazyZCode/launcher.js" status \
     --install-root "<install-root>" --project "<project-root>" --json
   ```

3. Choose one host route. The **`zcode-marketplace`** route is the default:
   in ZCode open **Settings → Plugin Management → Discover → “+” / Add Plugin
   Marketplace**, paste the launcher-reported market root directory (the
   folder containing `marketplace.json`), switch to the **Personal** tab, and
   **Install** the `lazyzcode` plugin card. For development-only validation,
   `zcode plugins validate plugins/lazyzcode` checks the manifest without
   installing anything.

4. Host configuration is validated before it is trusted. Stdio MCP
   servers require a non-empty executable name or path (spaces are supported),
   string arguments, and resolvable bundled launcher paths; a declaration that
   violates this reports a typed error naming the server and the remediation
   instead of loading silently.

5. Read the printed next action before claiming readiness. Status and
   load-check output separates package readiness from host readiness and names
   the remaining step. Enabling a plugin in ZCode is not a connection and does
   not by itself show that an MCP server is running.

6. Start a fresh ZCode session: host readiness requires a visible LazyZCode
   skill (Skill tool or **Settings → Skills**, Plugin Skills group) or command
   (a slash menu entry such as `/lazy-ulw-plan`) and all six MCP servers:
   `run-ledger`, `verification`, `status-dashboard`, `context-graph`,
   `code-intel`, and `docs`.

Until a host is observed in a fresh session, report **HOST READINESS: PENDING**
for every route above. The `manual-skills-mcp-fallback` route is
recovery-only and cannot coexist with the full plugin route for the same
project. Do not claim host readiness without fresh-session evidence.
